PHASE 2 — EQUIPMENT EXPANSIONS / LASER ORIGINS
==================================================
ANDROMEDA ADAPTATION — historically probable.

Rule / source of truth
----------------------
EquipmentSnapshot.GetExpansionStage(shipId) is the sole server rule.
Unmapped ID, capacity <= 0 or incomplete hull -> 1.
Full hull with mixed laser types -> 2. Full LF3 hull -> 3.
Drone lasers do not determine stage; their existing contribution to N/damage stays unchanged.
The active CharacterConfig chooses the existing immutable EquipmentSnapshot.
Stage is captured in LaserVolleySnapshot together with config/N/color/skill.
This is the approved Andromeda adaptation, not a certified Bigpoint historical rule.

Wire contract (text protocol)
-----------------------------
RDY|I: existing expansion field, zero-based split index 19 -> 1/2/3.
f|C: existing expansion field, zero-based split index 4 -> 1/2/3.
The initial object list uses the same C composer contract.
New server-only extension: 0|ES|userId|stage (normal map broadcast plus owner).
No inventory details. No remove/recreate. Same stage does not publish an ES.
Admin invisibility and existing map delivery rules remain in force.
Publish after A/B assignment and after successful existing website snapshot refresh.
No added query/polling. No new DB field/table/SQL.
Player attack extension: 0|a|attacker|target|visualLaserType|shield|skilledLaser|capturedStage.
The last field fixes the stage for this logical volley, even if ES arrives first.
HTML5 accepts old a packets by capturing the entity stage when that field is absent.
Invalid/non-positive/non-integer stage -> 1; values > 3 clamp to 3 for mapped ships.
Unmapped/legacy IDs including 2 and 58 -> 1, with no invented overlay.

Flash 4.1 policy
----------------
Correct stage on natural I/C login/spawn/jump. No promise of live A/B stage updates.
The local Flash text router ignores ES; its laser parser reads only the original fields.
No binary Unknown 1099 and no artificial R+C/respawn/recreation.

HTML5 assets / registration
---------------------------
SHIP_EXPANSION_DEFS maps ship -> expansionClass -> stage asset.
SHIP_EXPANSION_ASSETS defines the native frames and nativeOrigins.
Stage 1 has no overlay. A missing Emed never falls back to Emax.
Failed atlas requests are cached, with one diagnostic per path.
Atlas/sprite cache keys include asset, stage and orientation.
All assets have 32 orientations; new atlases use 8x4 cells, 1px padding and native pixels.
No frame resize, recolor or invented coordinate rotation.
Phase 2B: 18 new Unknown atlases (6 hulls + 6 Emed + 6 Emax), native 8x4 cells.
The 18 superseded HTML5 atlases are removed after validation. Historical SWFs stay intact.
The other Phase 2 families retain their previous assets and metadata.

Native registration is recovered from the SWF symbol bounds and alpha crop translation.
Per orientation, let C be the current hull raster, N the native raster, B the SWF bounds:
  hullOrigin = -size(C)/2 + alphaMin(C) - alphaMin(N) - min(B)
  registration = hullOrigin * entityScale - existingHullVisualShift
Overlay origin = native SWF bounds origin (new assets), or bounds + native alpha minimum
minus current alpha minimum (existing cropped assets). Drawing uses this origin plus registration.
Laser XML coordinates use the same registration in world units; the camera already scales them.
The current hull render anchor itself is unchanged. Overlays receive the existing hullY idle offset.
The Goliath correction follows the native pivot; no hardcoded -2.7px compensation.
32-frame hullOrigins/renderShifts are metadata of the current hull images, not a new equipment source.
If those hull images or the existing hull-centering algorithm change, regenerate/verify this metadata.

Vengeance / design exceptions
-----------------------------
8 uses the modern Unknown family matching the current hull, never the incompatible old local hull.
17 explicitly keeps expansionClass 8 and the same Unknown overlays as 8.
10 Emed comes from Unknown; Emax remains the compatible local asset.
56/59 use ship10_Emed and ship10_Ecombat from Unknown, expansionClass 56.
63..67 retain their own local Emed/Emax and XML patterns.

Salvos / gameplay preservation
------------------------------
game.xml provides every positionsList for 32 orientations; no approximate sin/cos rotation.
Stage patterns are expansionClass data, not laserClass (these player ships use laserClass 0).
Classes 1/3/4/5/6/7/8/9: [1] / [2] / [2,1,2,1].
Classes 10/56: [1] / [2,1,2,1] / [2,3,2,3].
Class 18: [1] / [2] / [2,1,2,1,2].
Class 63: [1] / [1,1] / [2,1,2,1].
Classes 64..67: [1] / [1,1] / [2,1,2,1,2,1,2,1].
Each RSB pulse reserves its next origins from the captured stage before scheduling its callback.
The existing 5 pulses, 120ms spacing, N and gameplay cooldown remain unchanged.
SAB keeps a single center-to-center ring per pulse, target -> attacker.
Skilled lasers change sprites only, with the same origins and beam count.
N, ammo delta persistence, damage/MISS, full-LF3 colors and PvP >45k behavior are unchanged.
NPC equipment stages are outside this patch; their existing maximum-pattern selection is retained.

Tests
------
Tests/ExpansionStageTests.cs: compile against the emulator and EquipmentPhase1Tests.cs,
select /main:ExpansionStageTests. Synthetic snapshots, actual composers, loopback sockets; no SQL.
htdocs/spacemap_html5/tests/expansion-stage.test.cjs: Node source-function/XML tests.
Optional argument 1: result JSON path; argument 2: packet file produced by ExpansionStageTests.
Existing Phase 1 and ammo-persistence regression harnesses remain applicable.
The full external report records actual test results and limitations; test harness coverage is not
a claim that authenticated web login, natural jump/respawn and mobile device testing were completed.
